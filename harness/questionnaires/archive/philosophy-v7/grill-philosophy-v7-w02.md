## Q1. 九个 skill 的生态位应如何治理,才能避免重叠和空洞？(D5+D7+D8)   [落盘: 处理报告;必要时进入 TODO]

- [ ]  A. 保持现状,只靠各 skill 的 description 和用户经验分流——不增加维护成本,但重叠和空洞只能靠事后发现

## Q2. 九个 skill 对哲学要求的覆盖,应达到什么粒度？(D1+D5+D6)   [落盘: 处理报告;必要时进入方法不变量/验证卡候选]

> **出题依据:**哲学 v7 的不可裁剪核心已在 ADR-0019 记录,但现有 skill 规格分别描述问答、压测、留痕、下放、跨会话和 harness 组织,还没有一张“哲学主张 → skill 责任 → 最小产物 → 当前状态”的活矩阵。

- [ ]  A. 只要每个核心 skill description 能找到相关哲学链接,就视为覆盖——维护最轻,但链接存在不等于能力实现或证据存在
- [ ]  B. 为哲学每条重要句子建立全量追踪矩阵,没有对应 skill 就视为缺陷——覆盖最强,但会把哲学变成大型规格索引
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. 只为四项不可裁剪核心及高风险路径建立最小覆盖矩阵,列明责任 skill、最小产物、当前状态和缺口;其余主张保留文档级链接——★推荐,因为把证据成本集中到真正改变安全边界的主张

## Q3. skill 命名是否已经足够望文知意？(D8)   [落盘: 处理报告;术语或触发词冲突进入 CONTEXT 修订建议]

## Q4. 当代码实践明显优于设计但偏离设计时,哪个对象应先被视为事实？(D2+D3+D7)   [落盘: 处理报告;偏差治理可进入 ADR / TODO]

> **出题依据:**哲学元原则与方法论检查清单要求“实现中发现设计要改 → 先更新设计文档,再改代码”;但真实实践可能先出现更好的实现,若强制代码服从旧设计会压制反馈,若直接接受代码又会形成设计-实现脱节。

- [ ]  A. 设计永远是唯一事实源,任何偏离先退回重做——一致性强,但可能把更好的实践当成违规
- [ ]  B. 代码运行结果优先,设计只在需要时补文档——反馈快,但容易让设计失去约束力并积累不可追溯偏差
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. 先把偏差分类:局部实现优化可在实现记录/retro 留痕,改变目标、约束、风险或接口的偏差必须暂停相关不可逆动作、更新 canonical 设计并重新交叉挑战;完成后代码与设计重新对齐——★推荐,因为同时承认实践反馈和设计治理的权威边界

## Q5. delegate 在实践中低使用率时,应如何判断它是失败、过早设计还是低频但有价值？(D1+D6+D7)   [落盘: 处理报告;必要时更新 OPEN-DECISIONS]

> **出题依据:**哲学把 delegate 作为纯执行类决策的横切机制;`skills/delegate/SKILL.md` 将它限定为白名单、禁区、收回条件和逐例日志,但当前仓库没有项目级 delegation 文件或日志实例。低使用率目前只能说明“尚未形成使用证据”,不能直接说明机制无价值。

- [ ]  A. 立即把 delegate 设为默认路径,通过强制使用获得数据——数据会更快出现,但可能制造形式主义使用和错误下放
- [ ]  B. 视为失败并从方法论主路径中移除——减少维护面,但可能过早放弃一个只在特定任务密集时有价值的机制
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. 保持 opt-in,选择 1–2 类低风险、可逆、可计数的执行决策做短期 pilot,预先定义使用率、收回次数、人工纠正和日志完整度信号,再由 retro 判断是否扩展——★推荐,因为区分“低频”与“无价值”,且不会为获取数据而扩大权限

## Q6. delegate “放权后不可控”时,最低控制闭环应是什么？(D2+D4+D6)   [落盘: 处理报告;若形成启用门,进入 OPEN-DECISIONS]

> **出题依据:**delegate 规格已有 `enabled` 总开关、白名单、禁区、单条目收回条件和逐例日志;但当前未在本项目真实 delegation 文件与日志上验证“启用 → 执行 → 发现异常 → 收回 → 复盘”的完整闭环。

- [ ]  A. 依靠事后查看日志和人工信任——实现成本最低,但无法保证异常发生时能及时止损
- [ ]  B. 在控制闭环验证前永久关闭 delegate——风险最小,但无法学习真实使用中的控制问题
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. 默认关闭,显式启用,每类白名单有收回条件,保留可立即关闭的总开关,每例实时追加日志,并用一次故障注入/撤销演练证明收回生效——★推荐,因为把“可控”定义成可停止、可追溯、可演练,而不是只存在配置字段

## Q7. 如何治理“未实测就假定”的信息真空？(D1+D4+D6)   [落盘: 处理报告;可进入方法不变量与 skill 共同前置契约]

> **出题依据:**grill-Q 与 action-Q 都已有“先调研、核实、实测再出题/列清单”的规则;哲学 §一把背景缺失视为核心返工机制。但现有规则分散在 skill 规格中,尚未明确哪些主张必须有原始命令/输出/最小调用证据,以及未验证时能否继续执行。

- [ ]  A. 继续依靠 agent 判断哪些事实值得实测,未实测的假定由用户自行承担——灵活,但正好把信息真空留在最危险的入口
- [ ]  B. 任何任务都必须完成全量环境实测后才允许继续——证据最强,但会让低风险、纯文档和可逆任务成本失控
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. 建立风险触发的证据前置:凡涉及工具/代码行为/外部依赖/不可逆动作的主张,必须附原文或可复现命令与输出;无法核实时标为未验证,高风险动作暂停,低风险动作可带状态继续——★推荐,因为把“先验证”变成有边界的执行门

## Q8. 如何阻止“轻量测试通过”被误读成“结论成立”？(D4+D6)   [落盘: 处理报告;可进入 L3 验证卡与实操 DoD]

> **出题依据:**OD-13 已实证 AI 自评通过与人类实际可用不等价;哲学 §4.1/§4.4 承认嵌套黑盒与形式化 V&V 缺口,实操只给出 L3 最低分流。当前尚无按风险区分“测试通过能证明什么、不能证明什么”的统一等级。

- [ ]  A. 测试绿即可作为当前结论,边缘场景留给后续反馈——速度最快,但会把局部证据扩大成整体结论
- [ ]  B. 所有产物都采用完整形式化 V&V、覆盖矩阵和 assurance case——独立性最强,但超出个人项目默认成本边界
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. 建立风险分层的最低 assurance:普通可逆代码可用客观测试并标明范围,AI 自写 oracle 要人审 oracle,用户可玩/单向门必须人试玩或确认,高风险或反例信号再升级覆盖矩阵/形式化方法——★推荐,因为让测试证据与结论强度匹配

## Q10. 是否需要新增一个跨 skill 的统一治理层？(D2+D3+D5+D6)   [落盘: 处理报告;若形成结构性新增,进入 OPEN-DECISIONS / ADR]
