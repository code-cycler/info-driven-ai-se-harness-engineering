## T1. 120k/400k 经验值:数字凭什么可信?   [落盘: 处理报告(方法论 §1.1 修订建议)]

**出题依据**:方法论 §1.1「对于 200k 上下文模型,有效上下文经验值约 120k;对于 1m 上下文模型,约 400k」——无来源标注、无测量方法、无代际复验方式。W01 Q2 已在 MC 卡补「模型行为假设」(主张层),但这两个**具体数字**的出处仍是悬空:作者主观体感?社区经验法则?某代际模型的实测?数字被读者当真(它们精确到千位),却没有一条证据链。第一性原理:一个体系若允许无出处的精确数字进入立论,它对所有数字的公信力都会被拖累——这与哲学对「经验性示例 vs 测量结论」的严格区分(§1.2)自相矛盾。

- [ ]  A. 补全证据链:标注数字来源;若为作者体感则明写「作者主观经验值,无系统测量」,并给复验方法(如「同任务不同上下文长度对照」)
- [ ]  B. 删数字保定性:移除 120k/400k,只保留「过载稀释注意力」的定性表述——数字不可靠就不给数字
- [ ]  C. 维持现状:经验值本就是经验值,读者应自行判断
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  D. 来源分级标注 ★推荐 —— §1.1 处补一句:「此为作者经验值(主观体感,无系统测量;约当窗口的 60% 与 40%),随模型代际漂移,无固定复验周期——更新触发 = 采用者主观察觉输出质量退化」。理由:A 的「系统测量」对个人开发者不现实(违反最小成本);B 因噎废食(数字对当前代际有锚定价值);C 让精确数字裸奔,拖累全文数字公信力;D 保留锚定价值 + 把数字的证据等级说透 + 给了更新触发,三行成本。

## T2. 误区清单溯源:24 + 11 条里,多少是实证、多少是想象?   [落盘: 处理报告(方法论 §八 / 哲学元原则表修订建议)]

**出题依据**:方法论 §八 24 条常见误区 + 哲学元原则表 11 条失败模式。逐条核对:有实证案例锚点的——引擎漂移(OD-8 diff 实证)、证据强度越界(OD-13「自评可玩 ≠ 人类可玩」)、skill 交接模糊(OD-22)、问卷形式主义(OD-14「想当然」信号)。但多数条目(分析瘫痪、文档形式主义、盲目信任 AI、设计-实现脱节、上下文膨胀、三层误读、双靶子失衡、(a)(b) 混淆、标准句脱节)无任何案例 ID——其中一批是压测产出的「防误读预防条」(标 ★),并非发生过的事故。第一性原理:清单混合了「发生过的事故」与「想象中的失败」,不区分时,读者会高估体系的实证密度(正是「证据强度越界」的第 25 种形态)。哲学对学科挂接都做了诚实标注,对自家清单反而没有。

- [ ]  A. 全量溯源:逐条标「实证(案例 ID)/ 预防(压测产出防误读)/ 推测(未发生)」三类——最重但最诚实
- [ ]  B. 不动:误区表本质是预防清单,不是实证报告,区分是过度治理
- [ ]  C. 删推测类:无案例 ID 又非压测产出的条目删除——清单瘦身
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  D. 表头分类注 ★推荐 —— 两张表(方法论 §八 / 哲学元原则)各加一行注:「本表混合**实证条**(有案例锚点,如引擎漂移→OD-8)、**预防条**(标 ★,压测产出的防误读规则,未发生事故)与**经验条**(源自通用工程经验,无本仓库案例)——三类证据强度递减,均属预防目的而非实证报告」。理由:A 工作量大且部分条目归属模糊(循环维护义务);B 放任「实证密度被高估」的误读;C 误删有效预防价值(想象的事故也是事故的预演——航空安全预想正是如此,只是别冒充实证);D 一次性说清证据等级,零逐条维护成本。

## T3. 任务类型表盲点:占比最高的「小改动」没有流程   [落盘: 处理报告(方法论 §零 修订建议)]

**出题依据**:方法论 §零「任务类型与流程适配」表覆盖五种:功能开发(完整闭环)/ Bug 修复 / 重构 / 依赖升级 / 探索性 Spike。日常开发中频次最高的**小改动**(改配置、调文案、修样式、微调参数)无行、无默认路径——表格呈「两端重、中间轻」:大 feature 与 Spike 都有流程,日常主体反而空白。读者只能自行猜测(走 action-Q?什么都不走?)。(a) 类盲区活例:流程定义了极端场景,漏了中位场景。

## T4. 验收侧的认知负荷:喂入侧有整套机制,审查侧只有原则   [落盘: 处理报告 + CONTEXT(已知缺口候选)]

**出题依据**:第一支柱在**喂入侧**(人 → AI)有完整机制链:design-Q 问卷、grill-Q 压测、有效上下文管理、落盘规范。但**验收侧**(AI → 人)只有原则性表述:「人审」「试玩」「签字权」「Code Review 不能省」。第一性原理的不对称:审查负荷是验收质量的决定变量——疲劳的审查者会签字走形式,这正是哲学 4.3「信任劫持」的入口;但方法论没有验收侧的「有效上下文」对等概念、无审查分批策略、无疲劳信号识别,唯一对策是「80/20 压低审查成本」(其本身未经量化验证,W01 已确认)。体系对「给 AI 的信息」精益求精,对「人接收 AI 产物的带宽」几近沉默。

- [ ]  A. 哲学 §四补「审查侧负荷」小节:论证审查带宽是人因瓶颈,与喂入侧对称立论
- [ ]  B. 方法论补审查操作规范:审查清单模板、分批审查策略、疲劳信号(连续 N 波零否决 = 警告,类推 OD-14 取消率设防)
- [ ]  C. 接受不对称:审查侧本质是信任与责任问题(第二支柱 + L3 分层已覆盖),不是信息问题(第一支柱不管)——不对称是分工使然,非缺陷
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  D. C + 显式承认 ★推荐 —— 采 C 的定性(不对称属分工边界),但在 CONTEXT「证据状态与范围」节或方法论 §1.1 补一条**已知缺口注**:「验收侧人审负荷管理无专项机制(现有对策 = 80/20 分层 + L3 风险分层,均未量化验证);审查疲劳 → 签字走形式 = 信任劫持已知入口,重访触发 = 出现『人审通过但事故』实例(与 OD-19 触发②共用)」。理由:A/B 都是新增机制(违反 Q7-A 冻结),且 B 的「连续零否决警告」与 OD-14 设防同构、可等试点数据后并入;C 不标注则缺口匿名——「未覆盖边界必须显式承认」是体系自己的规则(§3.3.2),D 只执行既有规则,零新机制。

## T5. 版本通胀:22 天 8 次升版,版本号的语义是什么?   [落盘: 处理报告 + CONTEXT(升版判据候选)]

**出题依据**:实测时间线:方法论 v2→v5、哲学 v4→v7,22 天内 **8 次升版**——哲学 v6→v7 仅隔 1 天,方法论 v4→v5 与哲学 v7 同日。每次升版都有压测/设计驱动,但驱动强度差异巨大(结构重组 vs 术语对齐)。同时哲学头部已有「修订记录」行(版本内修订留痕机制,W03 Q8 引入),但**升版判据**从未定义:本轮 W01 十项修订改了方法论/哲学正文内容,却不升版——那什么才配升版?第一性原理:版本号对读者的价值 = 可依赖的兼容边界(引用锚点、母本同步、ADR-0017 兼容映射都以版本为单位);边界随意时版本号退化为序号,兼容映射的维护成本(每次升版全库引用审查)被高频触发。
