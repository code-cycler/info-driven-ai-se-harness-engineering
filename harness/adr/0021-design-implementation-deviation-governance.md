# ADR-0021: 设计与实现偏差治理

- 状态:accepted(2026-08-14,grill-Q philosophy-v7 W02 Q4)
- 决策日期:2026-08-14

## 背景

实现可能先暴露比 canonical 设计更好的局部方案。若一律强制代码服从旧设计,会压制实践反馈;若直接把运行代码当作权威,又会让设计约束和风险取舍失去可追溯性。因此需要先判断偏差改变的对象,再决定是局部留痕还是暂停并更新设计。

## 决策

1. **局部实现优化**:如果偏差不改变目标、约束、风险、接口或验收标准,可在实现记录或 retro 中留痕;不要求立即重写 canonical 设计。若证明可复用,再进入方法或 skill 的后续修订。
2. **治理性偏差**:如果偏差改变目标、约束、风险、接口或验收标准,必须暂停相关不可逆动作,保留已有事实与副作用,更新 canonical 设计,重新进行双文件交叉挑战,再继续实现。
3. **代码是现实证据,不是自动的权威源**。完成裁决后,代码与设计必须重新对齐;不能靠覆盖设计或静默重试消除偏差。
4. **无法分类时按判断性决策处理**,由人确认偏差类别与下一步,不得由实现者静默归类。

## 替代方案(被否决)

- **设计永远是唯一事实源**:保持一致性,但会把有价值的实现反馈误判为违规。
- **代码运行结果永远优先**:反馈最快,但会使设计失去约束力并积累不可追溯偏差。

## 后果

- (+) 允许局部优化回灌,同时保留目标、风险和接口的设计权威边界。
- (+) 将“代码优于设计”从争论转化为可分类、可暂停、可恢复的治理路径。
- (−) 实现记录和 retro 需要明确偏差类别;误分类仍可能延迟发现。
- (−) 治理性偏差会增加一次设计更新与交叉挑战成本,但这是不可逆动作前的显式成本。
