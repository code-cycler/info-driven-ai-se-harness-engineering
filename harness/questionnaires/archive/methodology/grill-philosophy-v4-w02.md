## Q1. [软件工程 / D1 未言明假设 + D7 与现实矛盾] 代码审查行「AI✅辅助」与「AI 不做任何决策」核心原则的张力   [落盘: 处理报告(哲学修订建议)]

**出题依据**:哲学 [§6.1 分工表](docs/methodology/philosophy_v4.md#61-分工表)「代码审查 → 人✅ / **AI✅辅助**」,同一张表「决策(选什么方案)→ 人✅ / AI❌」,核心原则(§6.1)「AI 可以做任何事,但**不能做任何决策**」。但代码审查的本质是判断(approve / reject / request changes = 决策),且 [pr-review skill](skills/pr-review/SKILL.md) 自身声明「AI 永不 approve」。分工表给 AI「辅助」审查却没说明「审查里的**签字决策权**仍归人」——「决策行 AI❌」与「审查行 AI✅」表面矛盾,边界未言明。

- [ ]  A. 维持「AI✅辅助」不细化 —— 边界模糊持续,读者可能误以为 AI 可代审
- [ ]  B. 代码审查 AI 改回 ❌(仅人) —— 过严,浪费 AI 即时发现问题的能力
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. **细化分工表 + 脚注**:代码审查 = 人✅(最终 approve 决策)/ AI✅**辅助发现问题**,脚注「审查含大量微型判断,但**签字权(approve/reject)在人**,与 pr-review『AI 永不 approve』一致」  ★推荐 —— 消除「决策❌ vs 审查✅」表面矛盾,对齐 pr-review skill 现实,哲学层面一句话点清边界不过度展开

## Q3. [人因工程 / D1 假设 + D8 术语] 「上下文管理 人✅ AI❌」与 AI 实际做上下文管理的职责模糊   [落盘: 处理报告(哲学修订建议)]

**出题依据**:哲学 §6.1 分工表「**上下文管理**(给什么信息)→ 人✅ / AI❌」。但实践中 AI 大量做上下文管理:subagent 检索、design-Q preview 预答、读 CLAUDE.md 重建上下文、/compact 压缩。分工表没区分「**决定**给什么(人决策)」vs「**执行**检索 / 压缩 / 加载(AI 执行)」。人因视角:职责模糊会让人误以为「不用管上下文,AI 在管」——而上下文管理恰是第一支柱的核心人职责。

- [ ]  A. 维持「上下文管理 人✅ AI❌」—— 简洁但与 AI 实践脱节,读者困惑
- [ ]  B. 上下文管理改「AI✅辅助」—— 模糊了「决定权」,与核心原则冲突
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. **拆开定义**:上下文管理 = 「**决定**给什么信息(人✅ 决策,不可下放)」+「**执行**检索 / 压缩 / 加载(AI✅ 执行)」分工表注「决策权在人,执行可下放」  ★推荐 —— 区分决策与执行,既保「上下文决策在人」的核心原则,又承认 AI 的执行角色,符合 D1 显性化 + D8 术语清晰

## Q4. [软件工程 / D6 可验证性] 分工表的「辅助 / 执行 / 审阅 / ✅」无操作定义   [落盘: 处理报告(哲学修订建议)]

**出题依据**:哲学 §6.1 分工表混合使用 ✅ / 辅助 / 执行 / 审阅 / 逐类审查等词,但无操作定义。「辅助」到什么程度算辅助?「审阅」与「确认」区别在哪?「执行」是否含决定?作为**治理工具**,边界不可检查 = 退化成空话(违反 methodology §9「禁空话验收」)。

## Q5. [运筹学 / D1 假设 + D5 盲点] 「消除等人」被「等 AI」替换 + 单人吞吐量红利打折   [落盘: 处理报告(哲学修订建议)]

**出题依据**:哲学 [§6.2](docs/methodology/philosophy_v4.md#62-ai-替代的传统角色)「关键变化:不是 AI 替代了人,而是 **AI 消除了等人的时间**」。但 §1.3(W01 已改)承认瓶颈是「**等一轮 LLM 输出**」——AI 替代 PM/QA/Reviewer 后,这些角色活动变成「等 AI」。更关键:§6.2 的并行红利基于多角色假设(传统 4–5 人各自角色 → AI 同时承担),但 v4 §零受众收窄为「**个人开发者(单人)**」——单人串行调用 AI 时,「AI 替代多角色」的并行红利大幅缩水(一个人一次只能等一个 AI 输出)。红利来源被错认。

- [ ]  A. 维持「消除等人」叙事 —— 与单人受众现实脱节,运筹读者会指出 throughput 建模错误
- [ ]  B. 改为「AI 替代多角色执行,但单人用户仍串行等待 AI」—— 诚实但削弱卖点,可能过度悲观
- [ ]  🤔 我定不了 → 推迟/降风险
- [X]  C. **§6.2 加一句限定红利来源**:「AI 替代多角色**执行**,但单人开发者仍受『一次只能等一个 AI 输出』的串行约束;并行红利主要来自**消除角色间的人际等待与传递失真**,而非单人多任务」  ★推荐 —— 精确说明红利来源(人际等待 vs 单人多任务),与 §1.3 串行约束一致,符合 D1 显性化 + 运筹 throughput 精确性
