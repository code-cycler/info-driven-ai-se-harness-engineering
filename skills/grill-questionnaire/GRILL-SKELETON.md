# 压测维度骨架(grill-questionnaire 模板)

> 骨架 = 通用压测攻击面清单(D1–D8),不是内容题(区别于 design-Q 的 vision/hld/lld 内容骨架)。
> 问卷题目 = 把每个维度套到工件的具体声明上(工件驱动具体化,不得照抄维度名)+ 动态盲点。
> 覆盖度判定(终止条件的前提):8 维度全部套用过(代码库模式 D1–D8;纯逻辑模式 D1–D6)+ 工件每条**关键声明**(定义见 SKILL.md 第 1 步:决策点 / 假设 / 接口约束 / 验收标准;背景叙述与修辞不计)都被至少一个维度审视过 + 盲点清零 + 逃生舱项已全部进 OPEN-DECISIONS。

## 使用方式

- 每行给出:出题方向、落盘目标。出题时必须结合工件的具体声明具体化,不得只写维度名(如不能只问「有没有单向门?」,要问「工件第 3 节选了 Postgres,这是单向门吗?回滚代价多大?」)。
- 代码库绑定模式:D1–D8 全开。
- 纯逻辑模式(降级):只开 D1–D6(D7/D8 无代码库可查),并在处理报告里明确「未做现实对照」。
- 发现若满足 ADR 三条件(难逆转 + 会困惑 + 真权衡),同时写 ADR(见 PROCESSING-RULES.md)。

## 两模式通用维度

| # | 维度 | 出题方向 | 落盘 |
|---|---|---|---|
| D1 | 未言明假设 | 工件建立在哪些没说出口的假设上?逐条列出,标 成立 / 存疑 / 失效。常见入口:性能假设、可用性假设、用户行为假设、外部系统行为假设 | 存疑/失效假设 → 工件修订建议(处理报告);若支撑的是重大决策 → OPEN-DECISIONS |
| D2 | 单向门 / 可逆性 | 工件里哪些选择难逆转(数据迁移、公开 API 形态、认证方案、部署目标)?工件标了可逆性吗?该进 ADR 还是 OD? | 难逆转+会困惑+真权衡 → docs/adr/;其余单向门 → OPEN-DECISIONS(含重访触发条件) |
| D3 | 替代方案 / 被否决项 | 工件的关键决策是否给了被否决项?还是只有一个方案没权衡?逐个关键决策点追问「还考虑过什么、为什么不选」 | 缺失被否决项 → 工件修订建议;补齐后满足 ADR 三条件 → ADR |
| D4 | 失败模式 / 爆炸半径 | 出错时会怎样?能否降级/回滚?影响面多大?常见入口:依赖宕机、部分失败、超时、数据损坏、并发竞争 | 未覆盖的失败模式 → 工件修订建议;重大不可恢复风险 → OPEN-DECISIONS |
| D5 | 盲点(该说没说) | 工件该覆盖却没覆盖的:边界条件、错误路径、并发、回滚、迁移、容量、安全、可观测性 | 缺口 → 工件修订建议(处理报告) |
| D6 | 可验证性 | 工件的验收标准 / DoD 可检查吗?还是空话(「高质量」「性能好」)?能否脚本化/量化? | 空话 DoD → 工件修订建议(具体化到可检查) |

## 仅代码库绑定模式维度

| # | 维度 | 出题方向 | 落盘 |
|---|---|---|---|
| D7 | 与现实的矛盾 | 工件说 X,但代码 / CONTEXT / ADR 是 Y——这是压测最值钱的一项。逐条核对工件声明与既有实现、既有决策的冲突。**绿地模式**(项目存在但无代码,如纯设计期):「现实」从「代码」转为「既有设计文档/ADR/约束」——D7 = **工件内部一致性**(工件各部分自相矛盾,如 ADR 与 LLD 对同一数据结构选型不一致)+ **设计 vs 既有约束**(工件与已落盘 VISION/CONTEXT/ADR 冲突)。绿地模式 D7 仍有效(项目B dogfood Q15 抓出既有 ADR 与 LLD 不一致) | 矛盾 → 工件修订建议 + 必要时更新 CONTEXT/ADR(若既有决策已变) |
| D8 | 术语一致性 | 工件用词与 CONTEXT 定义是否冲突/重载/模糊?(工件说「订单」,CONTEXT 里「订单」是 Customer 还是 Order?) | 冲突/模糊 → CONTEXT.md 更新 + 工件修订建议 |

## 落盘契约(汇总)

- **工件修订建议**(D1–D8 发现的工件自身漏洞/盲点/缺失):进**处理报告**(对话内),grill-Q 不碰工件文件。其中可落实为「问题 → 行动 → 核验时机」的修订项同时写 `<项目根>/TODO.md`(同 design-Q/retro-Q,防发现落灰;懒创建;**不违反「不替改工件」——TODO.md 是追踪文件,不是工件**)。纯逻辑模式无项目根,可应用户要求持久化到 `~/notes/`。
- **修订建议排序(仅大问卷)**:本波问题数 ≥ 15 时,处理报告的「工件修订建议」按 单向门/安全 > 逻辑漏洞 > 盲点 > 风格 排序,防用户淹没(dogfood Q4 自定义「仅限 ≥15 题的大问卷」);< 15 题保持发现原序。
- **ADR**:满足三条件的决策(D2 单向门、D3 补齐的替代方案)→ `docs/adr/NNNN-<slug>.md`。
- **OPEN-DECISIONS**:单向门风险(D2)、重大风险(D4)、存疑假设(D1)→ `docs/OPEN-DECISIONS.md`(必填重访触发条件)。
- **CONTEXT**:术语冲突(D8)→ `CONTEXT.md`(纯术语表)。
- **归档**:已处理问卷移入 `docs/questionnaires/archive/`,文件名不变,尾部附处理报告摘要,只移不删。

> 维度集来源:2026-07-24 grill-with-docs 设计定稿(SKILL.md G3,DESIGN.md G3)。维度可随实践增减(增减属双向门,在 DESIGN.md 记一笔)。
> **安全无单独维度**:由 D1(安全假设)+ D4(安全失败模式)+ D5(安全盲点)交叉覆盖;安全关键设计的题在出题依据标「需人逐行审查」(安全非问卷能解,dogfood Q6)。
