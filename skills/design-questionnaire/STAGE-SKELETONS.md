# 三阶段固定骨架(design-questionnaire 模板)

> 骨架 = 每阶段必须覆盖的必问项,来自方法论(构想文档 / 全局设计 / 分阶段设计的必填内容)。
> 问卷题目 = 骨架未覆盖项(优先) + 动态盲点。
> 覆盖度判定(终止条件的前提):骨架项全部有答案(含已进 OPEN-DECISIONS 的逃生舱项)。

## 使用方式

- 每行给出:出题方向、落盘目标、是否必答。出题时必须结合探索结果具体化,不得照抄题干。
- feature 模式按文末「裁剪」节调整。
- 骨架项的答案若满足 ADR 三条件,同时写 ADR(见 PROCESSING-RULES.md)。

## Stage: vision(构想)

| # | 必问项 | 出题方向 | 落盘 | 必答 |
|---|---|---|---|---|
| V1 | 目标与受众 | 解决什么问题?给谁用? | VISION#目标 | ✅ |
| V2 | 范围 | 做什么;**明确不做什么**(边界与约束同样重要) | VISION#范围 | ✅ |
| V3 | 核心场景 | 用户怎么用?典型流程?用具体场景测边界 | VISION#核心场景 | ✅ |
| V4 | 验收标准 | 怎么判定做完了?必须可检查(能写进清单的才算) | VISION#验收标准 | ✅ |
| V5 | 风险与约束 | 技术限制、时间限制、依赖项 | VISION#风险与约束 | ✅ |
| V6 | 动机与推导 | 念头怎么长成方案的(构想文档记推导,不只记结论) | VISION#动机 | ⬜ init 选答,feature 必答 |

## Stage: hld(全局设计)

| # | 必问项 | 出题方向 | 落盘 | 必答 |
|---|---|---|---|---|
| H1 | 系统架构 | 模块划分、职责边界、数据流向 | HLD#架构 | ✅ |
| H2 | 技术选型 | 技术栈 / 库 / 协议 + 为什么;**被否决项也要记录**(防再提议) | HLD#选型 + ADR | ✅ |
| H3 | 接口契约 | 模块间 API、数据格式、通信方式(硬约束,实现阶段不能偏离) | HLD#接口契约 | ✅ |
| H4 | 部署与运维 | 怎么跑、怎么监控、怎么排查 | HLD#部署运维 | ✅ |
| H5 | 架构决策识别 | 本阶段哪些选择满足 ADR 三条件(难逆转 + 会困惑 + 真权衡) | harness/adr/ | ✅ |

## Stage: lld(分阶段设计)

| # | 必问项 | 出题方向 | 落盘 | 必答 |
|---|---|---|---|---|
| L1 | 阶段拆分 | 拆成几个可独立交付、可独立验证的阶段(不能独立验证 = 粒度太粗) | LLD#阶段计划 | ✅ |
| L2 | 详细设计 | 类图 / 序列图 / Schema / 状态机(按需,不必全画) | LLD#详细设计 | ✅ |
| L3 | 接口规格 | 入参出参、错误码 | LLD#接口规格 | ✅ |
| L4 | DoD | 每阶段完成验收条件(可脚本化的要脚本化) | LLD#DoD | ✅ |
| L5 | 依赖与预估 | 前置依赖、外部资源、大致工作量 | LLD#依赖 | ✅ |

## feature 模式裁剪

- **前置**:探索现有代码库与文档是必须步骤,问卷中凡涉及现有行为的题必须附出处(文件:行)。
- vision:V1–V4 保留(聚焦功能本身);V5 聚焦与现有系统的冲突风险;V6 必答(为什么是这个功能、为什么是现在)。
- hld:重点变为「与现有架构的契合点与差异」;H1 缩为「新增/修改哪些模块、现有模块哪些行为会变」。
- lld:不裁剪;每阶段 DoD 必须包含「不破坏现有功能」的回归验证。

## 阶段坍缩(可选)

默认按 vision → hld → lld 三阶段。定模时 agent 按「经验 × 规模」给坍缩建议,用户确认(主流程第 0 步)。坍缩后 vision 阶段不变,设计阶段二选一:

### 坍缩为 hld(没经验的项目)

用户缺乏相关经验、详细设计无法预先定 → 只做 hld(骨架 = 上文 hld 节,不裁剪);lld 不预先写,实现中边做边调整,沉淀的详细决策按落盘映射即时写入(必要时补 ADR)。

### 坍缩为 lld(小项目)

skill、脚本、小工具等架构显然的项目 → 不做 hld,直接 lld(骨架 = 上文 lld 节,不裁剪);H2 选型 / H5 ADR 识别若有实质内容,并入 lld 文档对应节或单独 ADR。
