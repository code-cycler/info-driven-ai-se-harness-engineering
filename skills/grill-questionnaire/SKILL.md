<what-to-do>

把「一问一答的 grill 压测」改为「多波次问卷的压测」:读一份已有工件,用固定压测维度 + 工件驱动的具体题生成一份 Markdown 问卷,用户离线作答后逐题解析,漏洞进处理报告、可沉淀项即时落盘。单次完整压测为主,按需补波,直到再无可压测的点。

## 术语

- **工件 (artifact)**:压测对象。一份已有、承载决策内容的文档——计划、决策记录、架构提案、ADR 草稿、HLD/LLD 草稿等。可以是项目里的文件,也可以是用户粘贴的文本。强调「已经存在、要被挑战」,区别于 design-Q 正在生成的「草稿」。

## 铁律(不可违反)

1. **AI 不替人决策** — 问卷提供 ★推荐 和利弊分析,选择永远是人的。agent 的角色是出题、验证、落盘。
2. **只产出发现,不替改工件** — 压测发现的工件漏洞/盲点只进处理报告(对话内),**绝不直接打补丁修改工件文件**。工件修订由人发起——发起机制是收尾时**主动询问**是否执行(见第 5 步,参照 grill-with-docs 的主动决策风格),用户授权后才落地,询问本身不等于替改。对标 retro「只记录不决策」。
3. **逃生舱绝不重问** — 用户勾了 🤔(或对话速答中表达「不确定/你决定」),走降风险协议(见 [PROCESSING-RULES.md](./PROCESSING-RULES.md)),不得换个说法再逼问同一题。**阻塞性分流非重问**:第 4 步的「转深钻」是人拍板的模式切换提议,不违反本条。
4. **即时沉淀,不批处理** — 每波处理完,可沉淀的发现(满足 ADR 三条件的决策、单向门风险、术语冲突)立即写入 CONTEXT / ADR / OPEN-DECISIONS,不攒到压测末。
5. **原始信息不丢失** — 问卷文件是唯一事实源;对话速答逐字转写进问卷文件;已处理问卷归档(只移不删)。
6. **先验证再出题**(代码库模式)— 凡要引用进问卷的「工件说 X、但代码/CONTEXT/ADR 是 Y」这类矛盾,主 agent 必须核实原文出处,不得凭转述出题。

## 主流程

### 0. 触发与定模

- **手动**:用户「压测/审一下/挑挑毛病/找漏洞」+ 指向工件(文件路径或粘贴文本)。工件未给则先要。
- **主动提议**:design-questionnaire 产设计草稿收尾时,用 AskUserQuestion 提议一次「要不要压测刚产出的设计?」。人确认后才执行。
- **判定模式**:
  - **代码库绑定模式**(默认):工件位于一个有 CONTEXT/ADR/docs/代码的项目里。能查「工件 vs 现实」的矛盾(D7)与术语一致性(D8)——压测最值钱的部分。**绿地子模式**(项目存在但无代码,如纯设计期):仍属代码库绑定,D7 的「现实」转为既有设计文档/ADR/约束(工件内部一致性 + 设计 vs 既有约束),D1–D8 全开;处理报告注明「绿地模式,D7 未对照代码」。
  - **纯逻辑模式**(降级):工件是游离的文本、无项目上下文(如粘贴的一段计划)。只跑 D1–D6 通用维度,不碰代码库;发现落 `~/notes/` 审阅报告,不写 CONTEXT/ADR/OD。明确告知用户「未对照代码库,建议在有项目上下文时复压」。
- **族间自检(批量 vs 单点)**:定模后核对一次输入形态——本 skill 的压测对象是**已成形的工件**(承载决策内容的文档);若输入实为**单个未成形问题**(依赖链深、下一问取决于上一问、需即时反馈)→ 用 AskUserQuestion 确认是否转 grill-with-docs 单点深钻,人不确认才继续问卷流程。判据锚 = 认知状态三态:知道·可离线答 → 批量;知道方向但未成形 → 单点;不知道自己不知道 → 对抗维度逼出(术语定义见 CONTEXT「Grill 家族」节)。

### 1. 读取与验证

- 读工件全文,提取**关键声明清单**。关键声明 = 决策点 / 假设 / 接口与约束 / 验收标准;背景叙述与修辞不强制审视(作为 G6 终止条件的可验证判据——dogfood Q7)。
- **超大工件分块**:工件为多章节大文档(整份 HLD+LLD)时,按声明组(如 HLD 章节)分块,每块独立压测,跨块矛盾单列成题。题量拆子波(第 2 步)管「题多」,工件分块管「工件大」,两维度分开(dogfood Q5)。
- 代码库模式:主 agent 快读 CLAUDE.md、CONTEXT、已有 ADR / OPEN-DECISIONS、工件涉及的代码区;读 `<项目根>/TODO.md`(若存在)。按需派 1–3 个 Explore subagent 核实「工件声明 vs 代码/既有决策」的矛盾点,subagent 只返回结构化事实清单(事实 + 出处)。
- 主 agent 对将引用进问卷的矛盾逐条核实原文,不做全量复核。
- 纯逻辑模式:只读工件自身,做内在一致性核验。

- **实测与调研前置(标准流程)**:提出问卷前,完成「调研现状 → 不假设 → 多实测 → 多获取信息 → 及时保存」闭环——
  1. **调研现状**:读 CLAUDE.md / CONTEXT / ADR / OPEN-DECISIONS / TODO / 相关代码区,不凭记忆出题;
  2. **不假设**:凡要引用进问卷的事实,不凭转述/记忆,必须核实原文或实测;
  3. **多实测**:不只查存在(`--version`/`brew list`),须实际跑通(编译链接 / 运行 / 调用级);证据(命令 + 输出 + 最小程序)记入出题依据;
  4. **多获取信息**:实测中发现的额外信息(版本差异、隐藏依赖、行为细节)一并记录;
  5. **及时保存信息**:证据与发现**立即**写入问卷出题依据 / 处理文件,不攒到出题后;无法实测的显式标「未验证假设」并放问卷最前(衔接问题级排序)。

- **轻量模式**:压测对象小、声明少、无外部依赖实测需求时,可对人提议走轻量管道——**AI 提议、人拍板,AI 无自裁权**(AskUserQuestion:「判为轻量压测,是否轻量执行?」)。轻量管道 = 调研只读 CLAUDE.md + 工件直接涉及的代码区(免 CONTEXT/ADR/OD/TODO 全量)+ 优先小波直问(≤3 题不上问卷文件)+ 免归档(处理摘要入对话);**不假设 / 先验证铁律不因轻量而豁免**(引用进问卷的矛盾仍须核实原文)。**初步结论先行**:AI 不追求「万无一失」才出手——先出初步压测发现请人轻验证(人勾/否/补一句),把「AI 全量验证」换成「AI 起草 + 人轻验证」,与 [OD-13](../../docs/OPEN-DECISIONS.md)「人类试玩通过才升级」/ OD-19「AI 自写 oracle 必须人审」同构,补其在轻任务层的缺位。

- **入口校准闸门(轻量模式豁免)**:出题(第 2 步)前向人出示**工件理解摘要**(一段话)+ **关键声明清单** + **压测焦点**(本波主攻维度/分块),AskUserQuestion 确认/纠正框架后才生成问卷——拦「理解框架级跑偏」(AI 误判答案材料的认知位置,整卷在错误框架内自洽;这是 CONTEXT「AI 同源出题限定」的体系内闸门)。轻量模式豁免(其「初步结论先行 + 人轻验证」同构);超大工件分块时每块各过一次闸门;闸门确认/纠正内容记入处理报告。

### 2. 生成问卷

- 问题来源 = **固定压测维度**([GRILL-SKELETON.md](./GRILL-SKELETON.md) D1–D8,代码库模式全开;纯逻辑模式只开 D1–D6)+ **工件驱动具体化**(把维度套到工件的具体声明上,不得照抄维度名)+ **动态盲点**(读取中发现的矛盾/未定义边界、上轮答案引出的新漏洞)。
- 格式严格按 [QUESTIONNAIRE-FORMAT.md](./QUESTIONNAIRE-FORMAT.md)。
- 写到 `harness/questionnaires/grill-<slug>-w<NN>.md`(slug = 工件短名,kebab-case;NN 从 01 递增),frontmatter `stage: grill`,status: pending。目录懒创建。**harness 文件分层见 HARNESS-RULES.md**(doctor-harness 规范权威,不内联复制)。
- 题量:每波上限 10 题;超出拆子波(`grill-<slug>-w<NN>a.md`、`…b.md`)。
- **小波阈值**:若本波问题数 ≤ 3,不生成问卷文件,改用 AskUserQuestion 直接提问(仍给 ★推荐与 🤔 逃生舱);问答与处理摘要逐字记入处理报告,追加到最近一份归档问卷尾部。
- **出题自检(强制,防遗漏)**:生成问卷后必须 grep 核对「每题要件齐全」——① 🤔 逃生舱数 = 题数;② ❌ 跑偏标注数 = 题数(FORMAT 规则 15,grill-Q 专属行);③ ✍️ 自定义行数 = 题数(每题 🤔/❌ 后必跟 ✍️ 自定义,FORMAT 规则 4,曾两次遗漏的 dogfood 教训);④ ★ 推荐至多每题一个。计数不等 = 问卷残缺,补齐后再交付用户。命令:`grep -c '🤔 我定不了' <问卷>`、`grep -c '❌ 这题跑偏' <问卷>` 与 `grep -c '✍️ 自定义: ____' <问卷>` 三者应相等且 = 题数。

### 3. 用户作答

- 默认:用户直接编辑问卷文件(`[ ]` → `[x]`、填 ✍️ 自定义行),保存后通知 agent。
- 也接受:对话速答,agent **逐字**转写进问卷文件,然后以文件为准解析。
- 用户宣布「答完了」之前不解析。

### 4. 处理与落盘

- 按 [PROCESSING-RULES.md](./PROCESSING-RULES.md) 逐题解析(含异常:单选多勾、必答未答、条件题误答)。
- 发现分两类落盘(本波处理完即刻写):
  - **工件漏洞/盲点/单向门/缺失替代方案** → **处理报告**(对话内),明确标为「工件修订建议」,人决定是否修订工件。grill-Q 不碰工件文件。其中涉单向门 / 安全 / 含新措辞裁量的修订建议按第 5 步「分层授权门槛」标 **⚠**。
  - **可沉淀项** → 难逆转+会困惑+真权衡写 `harness/adr/`;其余单向门/重大风险/存疑假设写 OPEN-DECISIONS.md(项目固有,路径不动);术语冲突写 CONTEXT.md。
- 纯逻辑模式:全部发现写审阅报告入 `~/notes/`(遵 `~/CLAUDE.md` 命名规范),不写项目 CONTEXT/ADR/OD。
- 🤔 逃生舱 → 降风险协议,绝不重问。**阻塞性分流**:若该题是后续题的依赖前提(它不定,后续题无法有效处理),不静默推迟——AskUserQuestion 让人拍板:① 推迟进 OD(现行降风险协议);② **当场转 grill-with-docs 单点深钻**该点,结晶后回本波继续处理。非阻塞题维持原协议;分流选择与深钻结晶逐字记入处理报告。
- 输出**处理报告**(对话内,格式见 PROCESSING-RULES.md):每题去向、新增/更新文件、异常处理、逃生舱处置、下一波候选、覆盖度(8 维度 + 工件关键声明审视情况)、**质量信号**(❌ 跑偏率 / 🤔 逃生舱率 / ✍️ 自定义率 + 被标 ❌ 题的归因——框架错 / 维度误用 / 事实错;同主题归因累计 ≥2 次 → 按 [ADR-0023](../../harness/adr/0023-skill-md-layered-slimming.md) 升格写入本文件规则本体;数据管道形态 provisional 见 OD-26)。
- 用户无异议 → 问卷 status: processed → archived,移入 `harness/questionnaires/archive/`,尾部附处理报告摘要。

### 5. 循环与终止

- 判据「**再无可压测的点**」:8 维度全覆盖(D1–D6 必全;D7/D8 代码库模式必全)+ 工件每条关键声明都被审视过 + 动态盲点清零 + 逃生舱项已全部进 OPEN-DECISIONS。
  - 还有 → wave+1(补充波),回第 2 步。
  - 没了 → 出示覆盖清单(8 维度 × 工件关键声明 的审视矩阵 + 落盘汇总),结束。
- 收尾:输出压测完成清单(发现的漏洞分类汇总 + 落盘的 ADR/OD/CONTEXT 文件链接 + 工件修订建议清单)。
- **主动询问是否执行修订**(参照 grill-with-docs 主动决策风格):完成清单输出后**不静默等待**,立即用 AskUserQuestion 问用户「是否执行压测产出的修订决定?」——把"是否落地修订"作为显式决策点,而非被动提醒后等用户想起。选项:① 立即执行全部修订建议(**⚠ 项除外,另行逐条确认**) ② 选择性执行(用户指定哪些条目) ③ 暂不执行(处理报告 + TODO 已留痕,用户稍后手动发起) ④ 🤔 不确定 → 降风险(列出最可逆切片先做)。用户确认执行后,按其选择落地修订——此时修订已经用户授权,不违反铁律 2(询问 + 授权 = 人发起,非替改)。同时提醒「若某漏洞是不确定性深水区,可对该点单独跑 grill-with-docs 单点深钻」。
- **分层授权门槛**:批量授权只覆盖「发现确认的机械落地」——作答时用户已逐题裁决修订方向的项。下列修订建议在处理报告标 **⚠**,选项① 不含、须逐条确认:① 涉单向门 / 安全类;② 含选项描述未写死的新措辞裁量(「怎么写」超出作答确认的「发现」范围,防裁量夹带);③ canonical 文件修订(另走 MC-04 交叉审查)。依据 = 判断性 / 纯执行术语边界(CONTEXT 人机分工节):作答裁决的是发现,批量下放的只能是无新裁量的落地。
- **可选:dogfood 验证** — 若压测对象是本家族 skill 的产物(如 design-Q 刚产出的设计草稿、或本 skill 自身的 DESIGN.md),收尾前可选项:用产物在真实小案例上完整走一遍闭环,缺口即时回修规格。用户可跳过;跳过与结果都记入 DESIGN.md。

## 与家族的分工

| | grill-questionnaire | grill / grill-with-docs | design-questionnaire | retro-questionnaire |
|---|---|---|---|---|
| 场景 | 压测已有工件(对抗式) | 实现期单点二义性、计划评审(单点深钻) | 启动初始化、功能设计(生成式) | 阶段/项目复盘 |
| 交互 | 多波次问卷,离线作答 | 一问一答,逐轮等待 | 多波次问卷,离线作答 | 多波次问卷,离线作答 |
| 骨架 | 固定压测维度 D1–D8(无内容骨架) | 无 | vision/hld/lld 固定骨架 | 四节 + Action Items |
| 落盘 | CONTEXT/ADR/OD + 工件修订建议(处理报告) | CONTEXT/ADR/OD | VISION/HLD/LLD/ADR/OD/CONTEXT | retro 文档 + TODO.md |
| 工件 | 只产出发现,不替改 | — | 生成工件 | 只记录,不决策 |

**闭环**:design-questionnaire 产设计草稿 → grill-questionnaire 压测 → 缺口回灌(OD/ADR/工件修订)→ 实现。write→review 两步都批量化。

压测处理中若发现某单点是不确定性深水区(一个漏洞引出大量纠缠子问题),在处理报告里建议用户对该点单独跑 grill-with-docs,然后回来继续压测流程。
