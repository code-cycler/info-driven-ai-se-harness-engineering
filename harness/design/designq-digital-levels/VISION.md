## 核心场景(V3)

- **大项目/多子系统**:多层(3 层以上),按子系统或深化需要加层;多层多文件形态(`harness/design/<feature>/L0-*.md …`)(W00 #10)
- **小项目/小 feature/小 action**:可**只有 L0** 单层交付(W01 定案:最小 1 层);L0 收尾闸门内置「是否需要细化」自检项(触发信号:多模块、外部依赖、跨会话实现等),触发才增层
- **层级职责模型(W01 定案:混合制)**:L0 固定 = 目标层(命名 `L0-vision`,承载目标/范围/验收,与「L0 恒在」基线一致);L1+ 浮动 = 职责由该层文档自声明(命名 `L1-<功能>` 式,如 `L1-contract` / `L2-build`),STAGE-SKELETONS 提供常用模板(契约层/构建层)作默认而非强制映射
- **动态插层**:实现期发现深度不足 → 插层(不回退不重构),过该层闸门 + 处理报告标注触发原因与影响面(W00 #7);与阶段回退协议互补:回退管「上游失效」,插层管「下游不够深」
- **层闸门**:每层独立闸门;插层/回退重开时只重过受影响层(W00 #14)

## 验收标准(V4,压测 W01 Q10-A 可核验化)

1. DOGFOOD 实测两个案例(小项目 2 层 + 中项目 3 层,含一次动态插层)——「走通」判据 = ① 案例产生 LN 产物;② L0 自检至少一次真实触发并留处理记录;③ 案例人确认可用
2. 全局实验版装载且本项目 backup 未动(OD-24);**全局更改前先 backup + 记录 diff 以便回退**;**改造前先全局⇄项目双向同步达成一致起点**(W01 Q2-C)
3. 「旧三档 100% 映射」判据 = 迁移映射表(doctor 产出)逐行有「旧语义 → 新落点」且旧三档每档产物字段在最小必含总览表有对应列,**人工逐行核对打勾**
4. STAGE-SKELETONS 反简化声明与最小必含全量核对通过(按层迁移后,W00 #12)
5. 存量改造 DoD = 「**标完即成档**」(交付 = 结构 + 缺口标注);待补项进 TODO 由人后续填,不算进改造验收

## 风险与约束(V5)

- **迁移丢失**:旧档语义映射不全 → 靠验收 3 + doctor-harness 迁移表对冲
- **双副本漂移**:全局实验版 vs 本项目 backup(OD-24;全局侧也先 backup,补充声明)
- **形式主义新变体**:层级制若过度模板化,小项目反而更重 → 靠「只有 L0」最小形态对冲(待 W01 定)
- **doctor-harness 职责膨胀**:从布局校验扩到存量改造,需守住「迁移/校验/留痕」的治理边界,不替用户做设计决策

## 设计原则(vision 闸门补充,2026-08-14 用户裁决——约束全部 hld/lld 设计)

1. **动态调整优先,反形式主义**:本项目强调动态调整,避免形式主义,**每个功能都要实用**——每个机制进规格前必答「解决什么实际问题?没有它会怎样?」答不出 = 不入规格(反简化声明的姊妹约束)。
2. **边缘场景显式设计**:一般情况下需要考虑边缘场景——**边缘场景是提升 UX 的地方**;hld 每个机制的设计与出题都要覆盖边缘场景(例:单层交付时插层协议如何触发?单文件多节形态下 L0 自检在哪做?插层插在中间层还是底层?)。
3. **最小必含总览**:最小必含项(STAGE-SKELETONS 反简化核心)需要**一个总览视图**——一处可瞰全部层的最小必含,不散落在各层段。
4. **文件头全局视野**:每个产物文件从开头就要有全局视野——开篇导览(本文在层级结构中的位置 / 覆盖什么 / 与其他文件的关系 / 阅读路线),参照哲学 v7 阅读路线与对标仓库 L1 阅读指南。
